## Decisions

1. **One sending domain per app, one Resend account per app.** The old account sent both Sudoku OTPs and Markd's public-signup verification mail from the same root domain; Markd's bounces appear to have burned the domain for both.
2. **`sudokucrew.com` for mail, `appfoundry.cc` stays for the API.** The API base URL is hardcoded in both shipped clients (`APIClient.swift:295`, `ApiClient.kt:24`) — moving it would brick installed copies. The reputation problem is outbound mail only.
3. **`.com` over `.cc`** for the new domain. `.cc` carries a higher spam association, and there was no reason to hand Gmail another negative signal while rebuilding reputation from zero.
4. **DMARC `rua=` must be on the sending domain** (`dmarc@sudokucrew.com`, caught by the catchall). RFC 7489 §7.1's external-destination rule means a `gmail.com` or `watsonblinds.com.au` address would require an authorisation record on *that* domain — so reports would silently never arrive.
5. **Don't delete the old Resend account** — Markd still depends on it.
6. **Speed mode needs a rebuild, not a patch.** See Notable Discoveries #6.

## Notable Discoveries

1. **Cached auth tokens hide a broken sign-in path indefinitely.** Every existing user (Derek, his dad, his daughter) holds a Keychain-cached bearer token and never re-authenticates, so nobody touches the email path once they're in. Account creation could have been broken for months with zero symptoms from the existing user base. Only new signups hit it — which is exactly the population least able to report a useful error.

2. **The bounce pattern split cleanly by provider.** Bounced: every Google-hosted address (`@gmail.com`, and Google Workspace `@watsonblinds.com.au`). Delivered: `@iinet.net.au`, `@sbcglobal.net`, `mail@ashgillett.com`. Teenagers are almost all on Gmail, so the friend group's failure rate was effectively 100% while the symptom looked like "it works for some people".

3. **A 204 from `/v1/auth/start` means Resend *accepted* the mail, not that it was delivered.** `sendOtpEmail` only throws on a non-2xx from the Resend API (`email.ts:20`), so the Worker cannot distinguish accepted-then-bounced from delivered. The real signal lives in the Resend dashboard. Worth remembering before trusting a 204 as proof of anything.

4. **A misleading first probe nearly settled the wrong diagnosis.** Testing with `test@example.com` returned 500, which looked like a smoking gun — but Resend rejects `example.com` specifically as a reserved domain. Real domains returned 204. Any probe address needs to be representative before its result means anything.

5. **A false doc is worse than a missing one.** `STATUS.md:76` claimed "SPF/DKIM/DMARC records added in Cloudflare DNS for the zone." The DMARC record had never existed. Finding it genuinely absent read as "here's the bug" and sent the diagnosis down an authentication path for a while — when the actual bounce message (`550-5.7.1 ... very low reputation of the sending domain`) showed authentication was fine and reputation was the problem. Corrected.

6. **Speed mode's real defect is a missing piece of state, not a bug.** There is no `activeNumber` in the model — the "armed digit" is inferred from the value of the currently *selected cell* (`SudokuGame.swift:282`). It half-works only because `enter()`'s tap-to-highlight branch (`SudokuGame.swift:347-356`) navigates selection to the first cell containing that digit, which incidentally arms it. Hence the frustrating behaviour: you cannot arm a digit that isn't already on the board, arming yanks your selection across the grid, and tapping any filled cell silently re-arms. All three review bugs are downstream of the shortcut living in `select()` — the only place with access to both the old selection and the new cell. `SPEC.md:190-194` documents the workaround as if it were the design.

7. **npm is broken machine-wide** (fails resolving its own internal modules under Node 18.17.1), so there is currently **no working deploy path** for the backend. Everything shipped tonight went through the Cloudflare dashboard.

8. **⚠️ Adding the `sudokucrew.com` Custom Domain took the entire backend offline.** Cloudflare *manages* the DNS record for a Worker Custom Domain, so replacing the existing entry rather than adding alongside it **deleted the `sudoku.appfoundry.cc` A/AAAA record**. Symptom: `curl` returned status `000` (connection failure, no HTTP response) and `Resolve-DnsName` reported "DNS name does not exist"; in-app it surfaced as the generic red "Something went wrong. Try again." Caught only because Derek's daughter tried to sign up during the window. Fixed by re-adding `sudoku.appfoundry.cc` as a second Custom Domain — **both must be listed**. Nothing was lost; D1 and all user data were untouched.

   **Why the old host can never simply be dropped:** four separate bindings are compiled into shipped app binaries — `APIClient.swift:295`, `ApiClient.kt:24`, `Sudoku.entitlements` (`applinks:sudoku.appfoundry.cc`), and `AndroidManifest.xml:37` (`android:host`). Plus the store listings' privacy URL and every multiplayer invite link already shared. `sudoku.appfoundry.cc` is the live host; `sudokucrew.com` is currently the spare. Consolidating would need a release through both stores *and* universal adoption — so the standing decision is to **keep both bound indefinitely**.

9. **A trivially reversible dashboard action caused a total outage, and nothing detected it.** There is no uptime monitoring on `sudoku.appfoundry.cc`. The `/health` endpoint exists specifically for this and nothing polls it.

10. **Restoring the DNS record did not restore service immediately for clients that had already tried.** The zone's SOA negative-cache TTL is **1800s**, so any resolver that queried during the outage cached "does not exist" for up to 30 minutes. Airplane-mode toggling and force-quitting the app did **not** help, because those clear the phone's cache but not the router's or carrier's recursive resolver. The fix was simply time — once her resolver's negative entry expired, the app worked on the next attempt with no further action.

    **The decisive diagnostic was loading `/health` in Safari on the affected phone, on both hostnames at once.** `sudokucrew.com` never stopped existing, so it was never cached as NXDOMAIN and served as a control: crew-works-plus-appfoundry-fails isolates the problem to that one hostname's resolver entry, while both-work proves the device has recovered and any remaining failure is elsewhere. Testing only the working host would have been a false all-clear. Worth reaching for again — a two-host comparison turns "it's broken" into three distinguishable answers.

11. **Every failure tonight — dead backend, missing DNS record, blocked email — presented to the user as the same red "Something went wrong. Try again."** That is the sole reason the session opened with "I'm not sure exactly what they're seeing." See the error-mapping item in `docs/TODO.md`.
